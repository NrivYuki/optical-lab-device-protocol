# Optical Lab Device Protocol 規格 第 1.0 版

OLDP は Optical Lab Device Protocol の略である。Optical Lab Demo Protocol と読んでもかまわない。

この規格は、vca-hub に通信方式を加える拡張の用例として作った、デモ用の規格の一例である。

眼鏡レンズの加工所(optical lab)で、機器(トレーサー・加工機など)とホスト(中継器・受注システムの窓口)の間でジョブ(玉型・処方・加工条件)をやり取りするための通信規格である。マイコンで動く機器を前提とする。

**これは独自の規格であり、The Vision Council が定める DCS(VCA 規格)ではない。The Vision Council による承認や関与はない。** DCS の項目の名前と単位を基準とし、通信の仕組みは新たに定めた。

DCS の機器とは直接つながらない。DCS から何を増やし、何を変え、なぜそうしたかは 14 章に示す。

この文書は CC BY 4.0(`docs/LICENSE`)の下で利用できる。`spec/` の定義とテストベクタは MIT(`LICENSE`)とする。

文中の「しなければならない」「してはならない」は必須の決まりを、「してよい」は実装が選べることを表す。

## 1. 目的と範囲

- マイコン(数十 KB の RAM、OS なし、浮動小数点演算の部品がないこともある)で動く機器が実装できること。
- LAN(TCP)を第一の方式とし、LAN を持たない旧機器はシリアル(UART。RS-232C などの線)でつなげること。どちらの方式でも同じ中身をやり取りする。
- 相手の確認と暗号化を必須とすること。
- 項目(ラベル)の名前と単位を VCA(DCS)に合わせ、ホストが DCS と相互に変換できること。
- 規格の正本は機械で読める定義(項目の辞書・フレーム・メッセージ・状態の番号)とし、文章は説明とすること。両者が食い違うときは、定義を正とする。
- テストベクタ(この入力ならこの出力になる、という例)を規格と一緒に配ること。実装は、それを通すことで規格どおりであることを示す。
- 長く変えずに使えること。法令や業界の規約のように時とともに変わる要求には、基本仕様(拡張を除いた部分)を変えずに、拡張(11 章・15 章)で対応する。基本仕様には、拡張では対応できない部分(フレーム・暗号・セッション・拡張の仕組みそのもの)だけを置く。

### 範囲外

- RS-485 で 1 本の線に複数の機器をつなぐ形(フレームに宛先の番号が要る)
- LAN の中で機器を自動で見つけること(機器にはホストのアドレスを設定する)
- 機器のソフトウェアの更新(必要な機器は 11 章の拡張で扱う)

### DCS との関係

- 項目の名前・単位・左右の書き方(右眼;左眼)は DCS に合わせる。
- DCS の機器とこの規格の機器は、ホストを間に置いてつなぐ。ホストが両方の形式を相互に変換する。
- 違いの一覧と理由は 14 章に示す。

## 2. 前提とする機器

| 項目 | 目安 |
|---|---|
| RAM | この規格の処理に 16 KB 程度まで(フレームの上限が 512 バイトの参照実装で約 7 KB。ジョブを 1 行ずつ読んで使えば、全体を置かなくてよい) |
| プログラム | 暗号を含めて 64 KB 程度まで(参照実装は H8/3069F で TCP/IP を含めて約 46 KB) |
| 時計 | なくてよい(証明書の有効期限を使わない。時刻が必要な機器は TIME でホストに尋ねる) |
| 計算 | 整数だけで実装できる(小数は固定小数点の文字列とし、整数として読む。10 章) |
| 乱数 | 下の「乱数」の決まりを満たす乱数源が要る |

### 乱数

機器は、ハンドシェイクの一時鍵を作るため、攻撃者が予測できない 32 バイトの値をセッションごとに作らなければならない。作り方は次のどちらかとする。

1. ハードウェアの乱数源(雑音など)の出力を、SHA-256 などで混ぜたもの
2. 製造時に機器ごとに入れた秘密の種(32 バイト以上。外へ出さない)に、動作のたびに変わる値(受けた文字の到着時刻など)を SHA-256 で混ぜたもの

2 の場合、種が漏れると、その機器の過去のセッションが解読される(前方秘匿性が種の秘密に依存する)。また、一時鍵が予測できると、機器はホストのなりすましを見破れない(Noise の `es` を攻撃者が計算できるため)。種は、静的鍵と同じように扱わなければならない。

## 3. 層の構成

```
  操作            PUT・GET・DATA・RESULT・AVAIL・INFO・TIME・PING (8 章)
  ────────────────────────────────────────────
  メッセージ      操作の番号・リクエスト ID・フラグ + 中身(VCA の行) (7 章)
  ────────────────────────────────────────────
  セキュリティ    Noise の手順で相手を確かめ、以後のフレームを暗号化する (6 章)
  ────────────────────────────────────────────
  フレーム        バージョン・種類 + 中身 (5 章)
  ────────────────────────────────────────────
  トランスポート  TCP: 長さを付けて流す / UART: CRC と区切りを付け、1 フレームずつ確認する (4 章)
```

機器は、常に接続を始める側になる。TCP では、機器がホストへ接続する。ジョブを受け取る機器は、接続したままにしてよい。ホストからの知らせ(AVAIL)は、その接続で送る。機器が接続を待ち受ける必要はない。

## 4. トランスポート

LAN(TCP)を第一の方式とする。UART は、LAN を持たない旧機器をつなぐための方式とする。

- LAN を持つ機器は、TCP を実装しなければならない。UART だけを実装してよいのは、LAN を持たない機器に限る。
- ホストは、TCP を実装しなければならない。UART は実装してよい。ホストまで線を直接引かず、シリアルと TCP の中継器を間に置いてもよい。

### TCP

- 各フレームの前に、フレームの長さ(2 バイト、上位バイトから)を付けて送る。
- 誤りの検出と再送は、TCP に任せる。
- ホストが待ち受けるポートの既定値は 33520 とする。この値は、設定で変えられなければならない。
- 2 未満の長さ、又は受けられる上限を超える長さを受けたら、接続を閉じなければならない。
- ホストは、ハンドシェイク中の接続の数に上限を設けなければならない(既定値は 8 とし、設定で変えられること)。上限に達しているときは、新しい接続を鍵の計算の前に閉じる。
- セッションは、TCP の接続ごとに 1 つとする。

### UART

線の設定は、8 ビット・パリティなし・ストップビット 1 とする。速度は、次の決まりによる。

- 速度は、9600・19200・38400・57600・115200 bps から選ぶ。既定値は 9600 bps とする。
- 全ての UART の実装は、9600 bps に対応しなければならない。それより速い速度への対応は任意とする。
- 実際の速度と上の値との差は、±2.5% 以内でなければならない。クロックによっては作れない速度がある(20 MHz の H8/3069F では、57600 bps は差が -1.36% なので使えるが、115200 bps は +8.5% になるので使えない)。
- 速度をセッションの中で取り決めることはしない。線の両端に同じ値を設定する。9600 bps のほかにも対応する実装は、速度を設定で変えられなければならない。機器は、対応する速度を説明書に書かなければならない。

速度を取り決める手順を持たない理由は、2 つある。第一の方式である LAN では、速度を物理層が決めるので、取り決めが要らない。UART でつなぐ旧機器は、DCS の機器と同じく、設置時に設定を合わせれば足りる。

線の上の 1 つのまとまりは、次の形とする。

```
COBS( 種類(1) + シーケンス番号(1) + 本体 + CRC-32(4、上位から) ) + 0x00
```

- COBS は、Cheshire と Baker の方法(0x00 を含まない形に詰める)である。CRC-32 は IEEE 802.3 のもの(`123456789` に対して `CBF43926`)で、種類から本体の終わりまでを対象とする。
- 種類: 0 = フレーム(本体は 5 章のフレーム)、1 = ACK(本体なし)
- 受ける側は、0x00 までを 1 つのまとまりとして読む。COBS を戻せないもの、短すぎるもの、CRC が合わないものは、何も返さずに捨てる。途中から読み始めても、次の 0x00 から拾い直せる。
- 送る側は、シーケンス番号を 1 つずつ進めて付ける(255 の次は 0)。機器は、セッションの始めに 0 から付ける。受ける側は、番号が連続していることを前提にしない(再送された 2 度目のフレームは、下のとおり番号と CRC で見分ける)。
- 受ける側は、正しく受けたフレームごとに、同じシーケンス番号の ACK を返す。
- 送る側は、フレームを送り終えてから 1000 ms 以内に ACK が来なければ、同じフレームを再送する。5 回再送しても ACK が来なければ、セッションを終える(9600 bps より遅い線では、待ち時間を長くしてよい)。
- 直前に受けたフレームとシーケンス番号も CRC も同じフレームは、再送されたものである。ACK だけを返して捨てる。
- シーケンス番号が同じでも、CRC が違えば新しいフレームとして受ける(機器がやり直すと番号は 0 に戻るが、ハンドシェイクの中身は毎回違う)。
- UART には、接続の切れ目がない。そのため、ホストはセッションの途中でも、種類 0x01 のフレーム(ハンドシェイクの 1 つ目)を受けたら、新しいハンドシェイクを前のセッションと並行して進めなければならない。前のセッションは、新しいハンドシェイクを最後まで終えて相手を受け入れるまで、捨ててはならない。受け入れたら前のセッションを捨て、応答を待っていた要求は全て失敗として扱う。受け入れなければ、前のセッションを続ける。
- UART のセッションが使える間(機器は受け入れの通知を受けた後、ホストは相手を受け入れた後)は、暗号で確かめられないフレームを理由にセッションを終えてはならない。失敗のフレーム、ハンドシェイクのフレーム(ホストが上のとおり扱うものを除く)、バージョンの違うフレーム、形の正しくないフレーム、暗号文を解けないデータのフレームは、何も返さずに捨てて続ける。解けないフレームでは、シーケンス番号を進めない。
- ACK を待つ間に相手のフレームが届いたら、受ける実装は、そのフレームを 1 つ預かって ACK を返してもよいし、ACK を返さずに相手の再送を待ってもよい。

## 5. フレーム

| バイト | 中身 |
|---|---|
| 0 | バージョン(0x01) |
| 1 | 種類: 0x01-0x03 = ハンドシェイク(6 章の 3 つのメッセージ)、0x10 = データ(暗号化したメッセージ)、0x7F = 失敗 |
| 2 以降 | 中身 |

- フレームの大きさの上限は、各実装が 9 章の `MAXFRAME` で申告する。全ての実装は、512 バイトのフレームを受けられなければならない。相手の申告を超える大きさのフレームを送ってはならない。
- 上限は、TCP・UART のどちらでも 65535 バイトまでとする。
- バージョンが違うフレームを受けたら、失敗(理由 1)を返して閉じる(UART の使用中は 4 章による)。説明には、受けられるバージョンを `supported=1` の形で書いてよい。
- バージョンの番号は、フレームの形と暗号方式の組を表す。暗号方式を替える必要が生じたときは、新しい番号で新しい組を定め、ほかの章は変えない。ホストは、複数の番号を同時に受けてよい。
- その時点で受けられない種類のフレームを受けたら、失敗(理由 4)を返して閉じる(UART の使用中は 4 章による)。

## 6. セキュリティ

### 方式

Noise Protocol Framework(第 34 版)の `Noise_XX_25519_ChaChaPoly_SHA256` を使う。機器が initiator、ホストが responder となる。prologue は、ASCII の `optical-lab-device-protocol 1` とする。暗号を省いた形は作らない(直結の線でも暗号化する)。

| 種類 | 向き | Noise のメッセージ | 暗号化される payload |
|---|---|---|---|
| 0x01 | 機器 → ホスト | `-> e` | 空 |
| 0x02 | ホスト → 機器 | `<- e, ee, s, es` | ホストのケイパビリティ(9 章) |
| 0x03 | 機器 → ホスト | `-> s, se` | 機器のケイパビリティ(9 章) |

- X25519 の結果が全て 0 のときは、ハンドシェイクを失敗にしなければならない。
- ハンドシェイクを終えた後は、機器からホストへのフレームを Noise の Split の 1 つ目の鍵で、逆向きのフレームを 2 つ目の鍵で暗号化する。nonce は Noise の決まりどおり(32 ビットの 0 と、64 ビットのリトルエンディアンのカウンタ)とする。カウンタは、フレームごとに 1 つ進める。再鍵交換(rekey)はしない。
- データのフレーム(0x10)の中身は、ChaCha20-Poly1305 の暗号文とタグである。付加データ(AD)は、フレームの先頭 2 バイト(バージョンと種類)とする。
- TCP では、暗号文を解けないデータのフレームを受けたら、何も返さずに接続を閉じなければならない。UART では、4 章のとおり捨てて続ける。

### 受け入れの通知

3 つ目のメッセージを送るのは機器なので、機器には、ホストが受け入れたかどうかが分からない。そのため、ホストは相手を受け入れたら、最初のデータのフレームとして、リクエスト ID 0・応答のフラグ付きの RESULT(`STATUS=0`)を送らなければならない。機器は、これを受けるまで操作を始めてはならない。

### 失敗のフレーム

失敗のフレーム(0x7F)の中身は、1 バイトの理由の番号と、それに続く UTF-8 の説明(省略してよい)である。暗号化はしない。理由の番号は、`spec/messages.json` の `fail` で定める(1 = バージョンが合わない、2 = ハンドシェイクに失敗した、3 = ペアリングしていない相手、4 = フレームの形が正しくない、5 = 必要な拡張に対応していない)。

失敗のフレームを送った側は、接続を閉じる。受けた側は、セッションを終える(UART の使用中は 4 章による)。失敗のフレームは認証されないので、受けた側は、それを理由に鍵やペアリングを変えてはならない。

### ハンドシェイクの時間

マイコンでは、X25519 の計算に数秒かかる。そのため、ハンドシェイク全体を 120 秒まで待たなければならない。120 秒で終わらないハンドシェイクは、閉じてよい。

### フィンガープリント

公開鍵のフィンガープリントは、次の手順で作る。X25519 の公開鍵 32 バイトの SHA-256 を求め、その先頭 10 バイトを上位のビットから 5 ビットずつ取る。それを Crockford の Base32(`0123456789ABCDEFGHJKMNPQRSTVWXYZ`)で 16 文字にし、4 文字ごとに `-` で区切る(例: `6069-S5G3-Q4N4-PEFD`)。

### ペアリング

- 機器は、製造時に静的鍵の組を持つ。鍵のフィンガープリントを、機器の画面に表示するか、ラベルに印刷する。
- ホストは、知らない鍵の機器が接続してくると、失敗(理由 3)で断り、ペアリング待ちとして画面に表示する。人が機器の画面又はラベルと見比べて「この機器を信じる」を選んだ後は、その機器を受け入れる。
- 機器は、人が機器を操作して「ペアリングの受付」にした間(5 分まで、かつ次のセッションまで)だけ、知らないホストの鍵を覚える。それ以外のときは、覚えたホストとしか通信してはならない(失敗の理由 3 で断る)。覚えたホストは、電源を切っても残さなければならない。
- 機器は、ホストのフィンガープリントを表示できなければならない。人は、ペアリングの後で、ホストの画面に表示されたものと見比べる。
- ペアリングを解除すると、その相手とは通信しなくなる。鍵が漏れたときは、機器の鍵を作り直してペアリングし直す。

### この方式の限界

- 機器は、ペアリングの受付の間、最初に接続してきたホストの鍵を確かめずに覚える。受付の間に攻撃者が先に接続すれば、攻撃者のホストを覚えてしまう。これは、受付の後に、機器が覚えたホストのフィンガープリントを見比べ、違っていれば解除してやり直すことで見つける。
- ホストの側は、人がフィンガープリントを見比べない限り、なりすましの機器を見分けられない。

## 7. メッセージ

データのフレームの中身(暗号を解いたもの)は、次の形とする。

| バイト | 中身 |
|---|---|
| 0 | 操作の番号(8 章) |
| 1-2 | リクエスト ID(上位から) |
| 3 | フラグ: bit0 = 続きがある、bit1 = 応答。ほかのビットは 0 で送り、受ける側は無視する |
| 4 以降 | 中身: VCA と同じ「ラベル=値;値」の行(ASCII、CR LF 区切り) |

- リクエスト ID は、要求を出す側が 1 から順に付ける(65535 の次は 1)。応答には、同じ番号を付ける。0 は、受け入れの通知だけに使う。
- 中身が 1 つのフレームに入りきらないときは、行の区切りで分け、最後のフレーム以外に「続きがある」のフラグを付けて、同じリクエスト ID で送る。分ける単位は、前から順に、フレームに入るだけの行とする。入る大きさは、相手の `MAXFRAME` から 2 + 4 + 16 バイトを引いたものである。
- 受ける側は、1 行ずつ読んで使い、全体を置かなくてよい。
- 1 行は、80 文字まで(CR LF を除く)とする。ラベルは英大文字で書く。
- 1 つのメッセージの中身は、256 KiB までとする。超えるものは `STATUS=5` で断る。
- 機器への要求(AVAIL・PING・TIME と拡張の操作)は、1 つのフレームに収めなければならない。
- 機器は、前の要求の応答を受けるまで、次の要求を出さなくてよい。ホストは、要求を順に処理しなければならない。

## 8. 操作

| 番号 | 操作 | 向き | 中身 |
|---|---|---|---|
| 0x01 | PUT | 機器 → ホスト | ジョブを送る。`JOB=` の行を最初に置く。応答は RESULT(`STATUS=`。捨てた項目があれば `IGNORED=`、受けられない値があれば `REJECTED=`) |
| 0x02 | GET | 機器 → ホスト | ジョブを求める。中身は `JOB=` の行(人が付けた名前)。応答は DATA。ないジョブには RESULT(`STATUS=1`)で答える |
| 0x03 | DATA | ホスト → 機器 | GET の応答。`JOB=` の行を最初に置き、機器が `LABELS` で申告した項目だけを入れる。玉型は `TRACE` に合わせる |
| 0x04 | RESULT | 双方 | 応答の結果(`STATUS=`)。機器は、DATA を受けた後、要求として `JOB=`・`STATUS=`・`IGNORED=`・`REJECTED=` を送る。ホストは、`STATUS=0` を受けてから、そのジョブを渡し終えたものとする |
| 0x05 | AVAIL | ホスト → 機器 | ジョブが用意できたことの知らせ(`JOB=`)。応答は RESULT |
| 0x06 | INFO | 機器 → ホスト | 加工の終了・機器の状態の知らせ(`JOB=` は省略可、`EVENT=` は DONE・ERROR・STATE のどれか、`TEXT=` は省略可)。応答は RESULT |
| 0x07 | TIME | 双方 | 時刻を求める(中身なし)。応答は TIME で、中身は `TIME=YYYYMMDDhhmmss`(協定世界時)。時計のない側は RESULT(`STATUS=3`)で答える |
| 0x08 | PING | 双方 | 生存の確認(中身なし)。応答は中身なしの PING |
| 0x80-0xFF | 独自 | 双方 | 11 章 |

- 応答は、要求から 30 秒以内に返さなければならない。30 秒以内に来なければ、要求を出した側は失敗として扱ってよい。
- 状態の番号(`STATUS`)の表は、`spec/messages.json` の `status` だけに置く。`STATUS=` の 2 つ目の値に、説明を付けてよい。
- 知らない操作や対応していない操作には、RESULT(`STATUS=3`)で答えなければならない。
- 形の正しくない行(`=` がない、ラベルが空、80 文字を超える)を含む要求には、RESULT(`STATUS=2`)で答えなければならない。
- PUT は、2 度受けても結果を変えてはならない。ホストは、`JOB` と中身が同じ PUT を受けたら、保存せずに `STATUS=0` で答える(応答が届かなかった機器が送り直す場合のため)。
- ホストは、ジョブを送信待ちにしたとき、接続中で受け取りのケイパビリティ(`LABELS` か `TRACE`)を持つ機器へ AVAIL を送る。機器が接続してきたときは、受け入れの通知の後に、その時点で送信待ちのジョブを新しいものから 8 個まで知らせる。AVAIL に応答したことは、ジョブを取りに来ることを意味しない。

## 9. ケイパビリティ

ハンドシェイクの 2 つ目と 3 つ目のメッセージで、互いに次の行を渡す(VCA の行の形)。

| 項目 | 必須 | 中身 |
|---|---|---|
| `VER=` | 必須 | 規格のバージョン(`1.0`)。`.` より前(メジャーバージョン)が違えば、失敗(理由 1)で断る。`.` より後ろだけが違うなら、通信を続ける。知らない項目は無視する |
| `DEV=` | 必須 | 機器の種類(DCS の DEV に合わせる。TRC・EDG など。ホストは HST) |
| `VEN=`・`MODEL=` | 必須 | メーカー・機種 |
| `SN=` | | 製造番号 |
| `MAXFRAME=` | 必須 | 受けられるフレームの大きさ(バイト)。512 より小さい値は 512 として扱う |
| `LABELS=` | | 受け取りたい項目の一覧(`;` 区切り。行を重ねてよい)。ないときは辞書の全ての項目 |
| `TRACE=` | | `点の数;E か U`(受け取りたい点の数と、等角度か不等角度か) |
| `EXT=` | | 対応する拡張の名前空間(11 章。`;` 区切り。行を重ねてよい) |
| `REQUIRE=` | | 相手にも対応を求める拡張の名前空間(`;` 区切り。行を重ねてよい) |

必須の項目がなければ、失敗(理由 4)で断る。相手の `REQUIRE=` に自分の `EXT=` にない名前空間があるとき、又は自分の `REQUIRE=` に相手の `EXT=` にない名前空間があるときは、失敗(理由 5)で断る。

`ACME:X=` のように名前空間を付けた項目を、拡張のために加えてよい。知らない項目は無視する。

## 10. 項目と玉型

- 項目の名前・単位・左右の書き方は、DCS に合わせる。定義は `spec/labels.json` に置く。
- 小数は、固定小数点の文字列(`DBL=18.00`)にする。小数点以下の桁数の上限は、項目ごとに定義で決める。機器は、10 の桁数乗倍した整数として読み書きする(浮動小数点を使わない)。上限より桁の多い値は「受けられない」とする。
- 整数と、10 の桁数乗倍した小数は、符号を除いて 9 桁まで(32 ビットの整数に収まる範囲)とする。超える値は「受けられない」とする。
- 持っていない項目は送らない(DCS の `?` は使わない。受けても、値としては受け付けない)。
- 玉型は、`TRCFMT=1;点の数;E か U;R か L;F・P・D` の行の後に、`R=`(半径、0.01 mm)の行を続ける。不等角度(`U`)のときは、`A=`(角度、0.01 度)の並びを添える。`R`・`A` は、80 文字に収まるよう行を分ける。点の数と合わない玉型は、受けてはならない。DCS の形式 2-4 は使わない。
- 受け取った機器は、DATA の行を次のどれかに分け、RESULT で返す。使った(返さない)、知らないか使わないので捨てた(`IGNORED=` にラベルの一覧)、値を受けられない(`REJECTED=`)。ホストはそれを記録し、人が分かるようにしなければならない。
- 項目の間の決まり(`BEVP` に応じて `BEVM`・`BEVC` が要る、など)は、`spec/labels.json` の `rules` に置く。決まりを破ったものは「受けられない」とする。
- `RESULT` の `STATUS` は、受けられない値か点の数の合わない玉型があれば 4、形の正しくない行があれば 2、それ以外は 0 とする。

## 11. 拡張

基本仕様を変えずに、要求の変化に応えるための仕組みである。メーカー独自の機能も、法令や業界の規約への対応も、ここで扱う。

- 拡張は、名前空間で区別する。名前空間は、英大文字で始まる英数字 2-8 文字とする。`OLDP` で始まる名前空間は、この規格に付属する標準の拡張(15 章)のために予約する。
- 拡張の項目は、名前空間を付けたラベル(`ACME:MODE`)とする。名前の部分は、英大文字・数字・`_` の 1-16 文字とする。名前空間は、ケイパビリティの `EXT=` で宣言する。
- 宣言していない名前空間の項目は、受けた側が捨てて `IGNORED=` で返す。
- 拡張の操作には、番号 0x80-0xFF を使う。中身の最初の行は `EXT=名前空間` とする。両方が宣言した名前空間のときだけ受け付け、それ以外は `STATUS=3` で答える。番号の意味は、名前空間ごとに決める。
- 0x09-0x7F の番号は、基本仕様のために残す。拡張に使ってはならない。
- 対応が欠かせない拡張は、`REQUIRE=` で相手に求める(9 章)。規約が特定の機能を必須とするときも、基本仕様を変えずにこれで表せる。
- 互換性のない変更は、同じ名前空間のままにせず、新しい名前空間(`ACMEV2` など)で定める。
- 文字で表せないデータは、Base64 などで行に入れる。1 行 80 文字と 1 メッセージ 256 KiB の上限は、拡張でも同じとする。
- ホストから機器への拡張の要求も、1 つのフレームに収める。大きなデータは、機器が要求し、その応答で受け取る。

## 12. 定義とテストベクタ

| ファイル | 中身 |
|---|---|
| `spec/labels.json` | 項目の辞書(名前・型・左右の有無・単位・取れる値・ほかの項目との条件) |
| `spec/messages.json` | フレームの種類・操作の番号・フラグ・状態の番号・待ち時間 |
| `spec/vectors/protocol.json` | COBS・CRC-32・UART のまとまり・TCP の長さ・フィンガープリントのバイト列。決めた鍵で行うセッション全体(ハンドシェイク・受け入れの通知・分割した PUT・GET・DATA・RESULT)のバイト列。UART の使用中に、暗号で確かめられないフレームを捨てて続けるときのバイト列(機器の側・ホストの側)。`REQUIRE=` の判定 |
| `spec/vectors/records.json` | 項目の扱い(使った・捨てた・受けられない・玉型の点の数) |
| `spec/vectors/noise_xx_25519_chachapoly_sha256.json` | Noise の公開のテストベクタ |

`protocol.json` は、`tools/gen-vectors.py` が参照実装を使わずにこの文書から作る。その暗号の部品は、RFC 7748・RFC 8439 の例と Noise の公開のテストベクタで確かめる。実装は、これらのテストベクタを全て通さなければならない。

## 13. 参照実装

参照実装は、別のリポジトリ [optical-lab-device-protocol-reference](https://github.com/NrivYuki/optical-lab-device-protocol-reference) に置く。機器の側は C(H8/3069F の基板で動くファームウェアを含む)、ホストの側は JavaScript で書かれており、12 章のテストベクタを全て通す。テストの内容、基板で測った値、実装の制限、確かめていないことは、そのリポジトリの文書に示す。

中身を文字(VCA の行)にした理由は、次のとおりである。参照実装を H8/3069F(20 MHz)で動かして測ったところ、両眼 1440 点の玉型のやり取りは、UART(9600 bps)で 90 秒余り、LAN(10BASE-T)で 30 秒以内に収まり、実用の範囲だった。また、1 行ずつ読めば機器に全体を置かずに済み、DCS との間で変換する必要もない。

## 14. DCS との違い

比較の対象は、DCS 3.14 とする。

### 同じもの

項目の名前・単位・左右の書き方(`右眼;左眼`)、`ラベル=値;値` の行の形、機器の種類(`DEV`)、等角度・不等角度の半径による玉型(`TRCFMT` の形式 1)。これらが同じなので、ホストは中身を作り直さずに DCS と相互に変換できる。

### 増やしたもの

| 項目 | DCS | この規格 | 理由 |
|---|---|---|---|
| 相手の確認と暗号化 | ジョブのやり取りにはない。TLS は、暗号化した面形状データを取りに行く接続でだけ使う | 全ての通信を Noise XX で暗号化し、互いの鍵を確かめる(6 章) | 処方とジョブが、LAN や遠隔の線を流れる。相手を確かめないと、盗み見や、偽のホスト・機器とのやり取りを防げない |
| ペアリング | ない | フィンガープリントを人が見比べ、覚えた相手とだけ通信する(6 章) | 暗号化だけでは、相手が本物かどうかは分からない |
| 受け取った項目の報告 | 知らない項目は受けた側が無視し、送った側には伝わらない | RESULT の `IGNORED=`・`REJECTED=` で項目ごとに返し、ホストが記録する(10 章) | 加工に関わる項目が黙って捨てられると、誤った加工になっても原因が分からない |
| ホストからの知らせ | セッションは、全て機器から始める | AVAIL でジョブの用意を知らせ、PING で生存を確かめる(8 章) | 機器が繰り返し尋ねなくても、ジョブができたときに取りに行ける |
| 要求と応答の対応付け | セッションを 1 つずつ終えてから次へ進む | リクエスト ID で、要求と応答を対応付ける(7 章) | 応答を待っている間にも、ホストからの知らせを受けられる |
| 同じ送信の 2 度目 | 定めがない | PUT は、2 度受けても結果を変えない(8 章) | 応答が届かなかった機器が、安全に送り直せる |
| メーカー拡張の名前空間 | 実験的な項目は `_` で始めるという決まりだけで、メーカーを区別する仕組みがない | `ACME:MODE` の形の名前空間を宣言し、宣言のない項目は報告して捨てる。独自の操作の番号と、対応を必須にする `REQUIRE=` も持つ(11 章) | メーカー間の項目の衝突を防ぎ、ホストを改造せずに拡張を通せる |
| 大きさの上限 | パケットの長さに上限がない | フレームは `MAXFRAME` で申告する(最低 512 バイト)。1 メッセージは 256 KiB まで、数は 9 桁まで(5・7・10 章) | RAM の少ない機器が、受ける前に必要な量を決められる。数が 32 ビットの整数に収まる |
| 機械で読める定義とテストベクタ | 文書の本文と表が定義であり、食い違う箇所がある | `spec/` の定義を正本とし、バイト列まで決めたテストベクタを配る(12 章) | 解釈の違いをなくし、実装が規格どおりかどうかを第三者が確かめられる |

### 変えたもの

| 項目 | DCS | この規格 | 理由 |
|---|---|---|---|
| シリアルのまとまり | FS と GS で囲み、予約文字をエスケープする。CRC は任意 | COBS と 0x00 の区切りを使い、CRC-32 は必須とする(4 章) | どこから読み始めても、次の区切りで拾い直せる。予約文字の扱いが要らない。誤りを必ず見つけられる |
| 確認応答 | ACK・NAK、確認応答の待ち 6 秒、送り直し 3 回 | シーケンス番号付きの ACK、待ち 1000 ms、再送 5 回(4 章) | 同じフレームの 2 度目を区別できる。短い待ち時間で早く立て直せる |
| 能力の取り決め | 初期化のセッションで、`DEF`・`D`・`ENDDEF` 又はプリセットの表を送る | ハンドシェイクの中で `LABELS=`・`TRACE=` を渡す(9 章) | 機器にプリセットの表を持たせずに済む。接続した時点で互いの能力が分かる |
| 玉型の形式 | 形式 1-4(バイナリの圧縮を含む) | 文字で半径を表す形式 1 だけ(10 章) | 実装を 1 通りにする。整数として 1 行ずつ読める。測定で、両眼 1440 点でも実用の範囲だった |
| 情報のない欄 | `?` を入れて送る | 持っていない項目は送らない(10 章) | 値の読み取りに例外を作らない |
| 接続 | シリアル、TCP のポート 50000・33512、UDP 33511 による告知 | TCP を第一の方式とし(既定のポートは 33520)、UART は LAN を持たない旧機器のために使う(4 章) | 速度の設定が要らない LAN を基本とし、機器から接続する形にそろえる |
| ハンドシェイクの時間 | 確認応答 6 秒、パケット 12 秒 | ハンドシェイクを 120 秒まで待つ(6 章) | マイコンでは、X25519 の 1 回に数秒かかる |

### 持たないもの

面形状データ(LDS・SDF)、ファイルでの受け渡し、`PROC`・`PROCBLK`、オートコネクト、`TIMEOUT` による待ち時間の変更は持たない。ジョブのやり取りに絞り、マイコンで実装できる大きさにするためである。必要なときは、11 章の拡張で運ぶか、ホストを介して DCS でやり取りする。

## 15. 標準の拡張

この規格に付属する拡張である。基本仕様とは別に、追加・改版する。

### OLDPKEY: 機器の鍵の交換

機器の静的鍵を、ペアリングをやり直さずに新しい鍵へ替える。

| 番号 | 向き | 中身 |
|---|---|---|
| 0x80 | 機器 → ホスト | `EXT=OLDPKEY`、`KEY=` 新しい X25519 公開鍵(16 進の小文字 64 文字)。応答は RESULT |

- 機器は、新しい鍵の組を自分で作る(乱数は 2 章の決まりによる)。
- ホストは、形の正しくない鍵、又はほかの機器が既に使っている鍵には、`STATUS=4` で答える。受け付けたときは、新しい鍵を今の鍵の機器と同じ機器として信じ、`STATUS=0` で答える。
- ホストは、新しい鍵でセッションを受け入れた時点で、前の鍵を信じるのをやめる。それまでは、両方の鍵を信じる(応答が届かなかった機器が、前の鍵で接続し直せるようにするため)。
- 機器は、`STATUS=0` を受けてから新しい鍵を使い始める。
- これは定期的な交換のための手順であり、鍵が漏れたときには使えない(前の鍵を持つ者も、同じ要求を出せるため)。鍵が漏れたときは、6 章のとおりペアリングを解除してやり直す。
